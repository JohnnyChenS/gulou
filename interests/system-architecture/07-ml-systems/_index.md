# ML Systems

## 阶段目标

建立从数据样本、训练评估到线上服务、监控和回滚的最小机器学习生命周期。完成后，你应能追踪一个预测结果使用了哪些特征、标签、数据切分和模型版本，并在评估或线上分布变化时安全停止或回滚。

## 进入条件

本阶段继承 Cloud Native / SRE 的部署、观测、SLO、发布和恢复边界，并把模型视为另一种需要版本化、发布和回滚的线上状态。同时继承 Data Architecture 的 Schema、数据质量与重放证据。本阶段不承诺讲完通用机器学习算法，也不承诺一个离线高分模型会带来线上业务收益。

## 这一阶段先把什么讲清楚

- **特征与标签**：特征是模型做预测时能获得的输入，标签是希望学习或评估的目标结果。两者都要写清生成时间、口径、版本和线上可用性。
- **训练/验证/测试集**：训练集用于拟合参数，验证集用于选择方案和调整，测试集只用于对未见样本做最终评估。切分方式要尊重时间、用户和业务边界，不能随意打散破坏现实时序。
- **泄漏**：当特征、预处理或数据切分偷看了预测时不可获得的未来信息、标签或同一实体的关联样本，离线指标会虚高。泄漏是时序和数据边界错误，不是通过换模型能解决的问题。
- **服务、版本与回滚**：服务化把特征查询、模型推理、超时、降级和观测放入请求路径。每个结果需关联数据、特征定义、代码、模型和配置版本；回滚时要同时验证这些版本的兼容性。
- **漂移**：数据漂移是输入分布变化，概念漂移是输入与目标的关系变化。监控要连接数据质量、特征分布、延迟、错误和有延迟的业务标签，并预定停止、降级、重训或回滚条件。

## 组件如何承载这些思想

Feature Store 可以管理特征定义与线上/离线取值的一致性，Model Registry 记录模型版本、评估和发布状态，Model Serving 承载批量或在线推理。这些组件不会自动防止泄漏、保证标签正确或决定回滚时机；数据和版本的可追溯关系才是它们共同要承载的设计。

## 综合项目产物

为推荐平台建立最小训练与推理链路，提交一份证据包：特征/标签定义和可用时间，带理由的训练/验证/测试切分，泄漏检查，离线与线上评估口径，每次预测的版本映射，漂移指标，以及一次发布、降级和回滚演练。

## 阶段挑战

设计一个离线指标优于旧模型、但线上特征分布和延迟已变化的发布场景。评审者必须先排除数据切分与泄漏问题，再根据 SLO、漂移和业务指标选择继续、降级或回滚，并说明回滚需要恢复哪些版本。

## 阅读顺序

先定义特征、标签和它们的可用时间，再完成训练/验证/测试切分与泄漏检查；接着连接模型服务、版本、监控、漂移和回滚。能用一份可追溯证据包评审新模型发布后，进入 Recommendation Systems。
