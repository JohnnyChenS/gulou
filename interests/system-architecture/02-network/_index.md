# Network

## 阶段目标

把一次远程请求看成一系列有状态、会等待且可能只完成一半的步骤。完成本阶段后，你应能解释超时、重试和排队如何相互放大，并用证据区分服务端变慢与网络丢失。

## 进入条件

已经有一个可观察的单机服务，能识别线程等待、队列和背压。现在把其中一个调用拆到另一个进程或节点，并为客户端、网络路径和服务端分别保留观测点。

## 这一阶段先把什么讲清楚

按请求实际经历的顺序理解六个机制：

1. **连接状态**：DNS、建连、加密握手、连接池取用和连接关闭都可能独立等待或失败；先明确客户端认为连接处于什么状态，服务端是否看到了同一连接。
2. **超时**：超时是等待方停止等待的本地决定，不证明对端没有收到或执行请求。不同阶段的超时需要独立预算，并保留请求标识来追踪超时后的真实结果。
3. **重试**：重试会再发送一次工作，只有操作幂等、重试预算受控且剩余时间足够时才可能改善成功率。若原始请求率为 λ、每次请求平均额外重试 r 次，则下游承受的 offered load 约为 `λ × (1 + r)`；失败率升高时，这个反馈环可能压垮正在恢复的服务。
4. **排队**：连接池、代理和服务端工作池都会保存尚未处理的请求。服务时间一旦逼近容量，等待会非线性增长，而调用方看到的只是总耗时变长。
5. **尾延迟**：高分位延迟揭示少数请求受到排队、丢包重传或慢实例影响；一个请求扇出到多个下游时，最慢分支更容易决定整体完成时间。
6. **限流**：限流在入口处拒绝或延后超出预算的工作，为下游保留恢复空间；必须写清按谁计数、在哪一层执行，以及被拒绝请求是否会被再次重试。

**部分失败**是指一个参与者仍在推进，而另一个参与者延迟或不可达。它使客户端观察到的超时与服务端实际执行结果不再等价，也是远程调用不能照搬本地函数语义的根本原因。

## 组件如何承载这些思想

Nginx 或 Envoy 可以承载连接终止、路由、超时和限流，Netty 与 gRPC 可以展示连接池、协议复用和请求截止时间，服务网关或 Service Mesh 可以统一策略与遥测。组件不会自动给出正确语义：超时预算、幂等边界、重试责任和请求标识仍需由架构设计明确。

## 综合项目产物

从单机服务中拆出第一个远程服务，画出客户端建连、发送、服务端排队与处理、响应返回的请求时间线。记录各阶段超时、重试次数、队列深度、服务端处理时长、连接与丢包/重传证据，并写出限流触发后的用户结果。

## 阶段挑战

计算正常与故障场景下重试如何改变 offered load，并判断限流能否打断放大环。随后给出一组能区分两种假设的证据：若是服务端变慢，应能看到服务端已接收请求、队列或处理耗时增长；若是网络丢失，应能看到握手/发送/确认缺口、重传或路径侧异常，而服务端可能没有对应请求记录。

## 阅读顺序

先沿一次请求依次学习连接状态、超时、重试、排队、尾延迟和限流，再用故障注入比较服务端变慢与网络丢失。能够解释部分失败、算清重试流量并完成证据判断后，进入 Distributed Systems。
