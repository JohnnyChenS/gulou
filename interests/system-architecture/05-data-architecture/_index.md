# 数据架构（Data Architecture）

## 阶段目标

建立从数据产生、传输、处理、存储到消费的完整生命周期，并能在迟到、乱序、重复和作业失败时说明数据取舍、恢复起点与正确性边界。完成本阶段后，你应能用 Schema、数据质量和重放证据评审一条数据链路，而不是只画组件图。

## 进入条件

已完成 Data Systems 的存储决策，能说明主要访问模式、提交与恢复语义，并已选定一类需要跨系统传递的事件。进入本阶段前，先写清事件的唯一标识、Schema 版本、生产者、消费者、保留时间和可接受的丢失或迟到边界。

## 这一阶段先把什么讲清楚

先沿一条事件的生命周期建立共同语言。**Event Time（事件时间）**是事件在业务世界发生的时刻；**Processing Time（处理时间）**是计算系统真正处理它的时刻。两者不同，手机离线、网络拥塞或重试都可能让早先发生的事件更晚到达。

**Window（窗口）**把无界事件流切成可计算的时间范围；**Watermark（水位线）**是系统对“事件时间大概已经推进到哪里”的判断，不是所有早期事件都已到达的保证。水位线越谨慎，结果通常越完整但等待越长；越激进，越早出结果但更多事件会成为 **Late Event（迟到事件）**。迟到策略要明确是丢弃、更新旧结果、送入侧输出，还是等待后续重放。

例如，平台按事件时间计算 10:00–10:05 的点击数，用户在 10:02 的点击因离线到 10:12 才到达，而水位线已越过 10:10。这条记录就是迟到事件：若业务允许修正，作业应更新原窗口并向下游发出带版本的更正；若不允许，也必须保留丢弃数量和原因，不能让报表静默偏差。

有状态计算会为窗口、键或运算符保存 **State（状态）**。**Checkpoint（检查点）**把某个受控状态切面与输入位置一起保存；失败后的 **Replay（重放）**从已验证检查点重读后续事件并重建状态。检查点只有在存储可读、输入仍保留、Schema 可解释，且下游副作用可幂等、事务化或补偿时才能支撑端到端恢复。

## 组件如何承载这些思想

理解上述生命周期后，再把 Kafka 看作可保留、可定位的事件日志，把 Flink 看作事件时间、水位线、有状态计算与检查点的实现例子，把 Spark 用于批处理或流批处理的对照。Iceberg 可以承载带 Schema 演进和快照的表，数据仓库则面向稳定的分析口径与查询。组件名不替代契约：仍要写清事件时间从哪里来、水位线如何生成、检查点包含什么，以及重放如何处理外部副作用。

## 在全景业务链中的深入落点

本阶段负责 Kafka consumer 之后的事件处理分支：消费进度进入流作业，按事件时间处理窗口、迟到事件和状态，并用 checkpoint/replay 恢复。这里必须同时区分两个“水位”：Kafka high watermark 约束复制日志的消费者可见性；Event Time watermark 表示流处理对事件时间推进的判断。它们的名字相似、所有者不同、失败后果也不同，不能在业务链图中合并成一个落盘或处理完成标记。

## 综合项目产物

为 AI 内容推荐平台提交一份**数据正确性与重放证据包**，至少包含：生产者和消费者共同审阅的 Schema/数据契约与兼容性决策；完整性、唯一性、时效性和口径一致性的数据质量规则及告警记录；以及记录检查点 ID、输入位置、版本、迟到策略、重放范围和 sink 校验结果的恢复演练。

## 阶段挑战

对上述 10:02 迟到事件注入重复、乱序、Schema 变更和检查点失败，分别推演窗口结果、下游更正和业务指标会怎样变化。使用证据包回答：最后一个可恢复点在哪里，最早可重放位置是什么，重放是否会重复外部效果，以及哪些“exactly-once”结论仅在某个组件边界内成立。

## 阅读顺序

先沿事件时间与处理时间的差异，依次理解窗口、水位线、迟到事件、状态、检查点和重放；再阅读 [Checkpoint 与 Replay：有状态流作业的恢复边界](checkpoint-and-replay.md)并完成证据包。能用一次失败演练证明 Schema、数据质量和重放边界后，进入 Cloud Native / SRE。
