# 系统架构课程作者规范

本规范面向已有多年工程经验的作者。正式知识单元首版只面向“已有多年开发经验、熟悉至少一种主力语言和常见 Web 基础设施”的工程师。课程先解释思想和约束，再落到组件；它不是组件 API、框架选型清单或排行榜。不得把正文扩展为零基础编程或计算机本科教材、面试或认证训练，也不得承诺岗位晋升或学习结果。

## 正式知识单元的固定结构

正式知识单元由“读者定向块”和“核心内容块”两部分组成。读者定向块必须先回答本页讲什么、解决什么问题、关键词是什么意思以及它在路线中的位置；核心内容块必须按以下十一项标题书写，且顺序不变：

```markdown
## 一句话理解
## 本页要解决的问题
## 本页词汇
## 在路线中的位置
```

```markdown
## 学习目标
## 先修知识
## 问题场景
## 第一层：底层思想
## 第二层：组件设计落地
## 第三层：生产实践与真实案例
## 第四层：动手验证与架构判断
## 常见误区与适用边界
## 掌握度检查
## 在综合项目中的应用
## 权威来源与延伸阅读
```

读者定向块不是装饰性摘要：它是正文推理的入口。每个正式单元至少要提供 6–10 个本页真正会使用的关键词，并在第一次使用前给出中文解释；只有协议、API、配置项和产品名保留英文原名。

## 读者理解契约

本课程的读者可以有多年开发经验，但不假设他同时熟悉操作系统、网络、数据库、分布式系统、SRE 和 ML。可以省略基础语法，却不能省略跨领域概念之间的连接过程。作者和 AI 在写作时必须遵守以下规则：

1. **首次出现要补齐四件事。** 每个承载后续推理的概念，第一次出现时至少说明“它是什么、为什么需要、在当前业务链的哪一步发生、如何观察或验证”。若只需知道名字，也要明确写成“本页不深入”，并链接到负责该概念的页面。
2. **结论不得跨过隐藏状态。** 使用“因为、因此、但是、不等于、只有在……时”把前置状态、状态变化、责任组件、可观察证据和结论连起来。不要从一个 API 返回值直接跳到业务保证。
3. **先走最小例子，再抽象规律。** 每个正式单元至少有一个可跟踪的事件、请求或状态变化示例。示例必须标出正常路径、可能等待的地方、分支条件和确认边界，然后再总结一般模型。
4. **区分同步、异步和并行。** 如果多个组件可能并行或异步运行，必须说明哪些是同步关键路径、哪些是后台分支，以及什么配置或业务选择会让后台分支成为响应前置条件。
5. **把“不能推断什么”写出来。** 每个重要观察都要同时写出它不能证明的更强结论，例如“消费者可见”不等于“物理介质已持久化”，“数据库页未命中”不等于“进程发生 major Page Fault”。
6. **术语按需要分级。** “现在必须理解”的术语进入正文、词汇表和示例；“需要知道但本页不深入”的术语给一句话解释和链接；“明确暂缓”的主题写出暂缓原因和后续页面。不要用一串未经解释的英文名词代替教学。
7. **每段只引入有限的新负担。** 一段文字可以包含多个相关术语，但不得让读者同时解码新的组件、协议、指标和故障模型。若推理需要跨页，先给一句中文桥接，再链接到下一页。

## 每层的最小写作骨架

四层学习法不仅规定内容顺序，也规定每层必须让读者完成的推理：

| 层 | 最少要写清楚 |
|---|---|
| 第一层：底层思想 | 一个具体现象；涉及的状态和拥有者；约束与故障模型；状态为何按这个顺序变化；可观察的证据；不能外推的结论 |
| 第二层：组件设计落地 | 组件如何承载前述状态和约束；接口/配置在链路中的位置；正常与失败分支；组件明确不承诺什么 |
| 第三层：生产实践与真实案例 | 输入和约束；按时间顺序的症状；调查证据；处置决策；预防措施；哪些条件改变结论 |
| 第四层：动手验证与架构判断 | 隔离环境；可复现步骤；预期观察；成功条件；清理方式；如何把观察转换成架构取舍 |

如果某层只能写出组件名或结论，不能写出状态变化和证据，就说明该层还没有完成，不应通过压缩文字来掩盖缺口。

## 可读性自检

提交或扩写前，作者必须逐项检查：

- 本段首次引入的每个关键术语是否已有中文解释？
- 每个结论前是否写出了必要的“因为/因此/但是/只有在……”？
- 是否明确区分线程计算、调度等待、I/O 阻塞和队列积压？
- 是否把业务链中的同步路径、异步分支和可并行步骤标出？
- 是否说明了当前观察不能证明的更强结论？
- 读者能否只依据本页和链接页面复述状态变化，而不必立即打开搜索引擎补概念？
- 需要暂缓的背景知识是否被标记，并指向负责它的后续页面？

## 四层问题契约

| 层 | 必须回答的问题 |
|---|---|
| 第一层：底层思想 | 这个问题的状态、约束、失败模型与不可绕过的权衡是什么？ |
| 第二层：组件设计落地 | 组件以哪些机制、接口和配置承载这些约束；它们分别不承诺什么？ |
| 第三层：生产实践与真实案例 | 在可核验的真实环境中，哪些条件、症状、观测和决策使这些边界重要？ |
| 第四层：动手验证与架构判断 | 学习者如何通过可复现观察验证假设，并在给定约束下说明选择或不选择？ |

## 证据、比较与案例

- 组件比较必须以工作负载、状态模型、故障边界、运维约束和成本为条件；不得写成脱离条件的排行榜、总分或“最佳”结论。
- 真实案例采用：`案例类型：真实案例（公开来源：<URL>；访问日期：YYYY-MM-DD）`。没有可核验公开来源，不得标为真实案例。
- 模拟案例采用：`案例类型：模拟案例（假设：<明确输入、故障与约束>）`。模拟案例不得暗示真实流量、客户或事故。
- 版本性事实采用：`组件版本：<版本>；官方页面：<URL>；访问日期：YYYY-MM-DD`。未写清三项，不得把版本行为写成事实。
- ChatGPT 对话只能帮助起草或生成问题，不能作为事实来源。Khan Academy 和其他外部材料只允许链接或按许可引用；不得复制受限制的正文、视频或题目。

## 活动与掌握度检查

每项活动必须明确：**环境、步骤、预期观察、成功条件、清理方式**。活动应验证一个可观察的假设，不得把命令成功或服务启动当作架构结论。

掌握度问题至少各覆盖一次：

1. **解释**：说明机制为何存在及其边界。
2. **应用**：在给定约束下选定机制并说明证据。
3. **迁移**：将同一思想应用到不同组件或故障模型。
4. **不使用**：说明何时不应使用该机制或组件，并提出替代方案。

## 禁止项与篇幅

不得出现 `TODO`；不得伪造流量、事故或案例；不得把 ChatGPT 回答当来源；不得依赖 `gulou-agent`。单篇以完整解决一个问题为准，不设机械字数指标。
