# 云原生与 SRE（Cloud Native / SRE）

## 阶段目标

把“能运行”的系统变成“可持续运营”的有状态服务。完成本阶段后，你应能分开说明编排层如何恢复计算实例、存储和应用协议如何恢复业务状态，并用 SLO、发布记录和恢复演练证明系统在故障后可控。

## 进入条件

已完成 Data Architecture 的 Schema/数据质量/重放证据包，能标出每份持久状态的所有者、恢复来源和最新可用恢复点。准备一个可部署的服务和一种可丢弃的隔离环境，不将生产数据、凭证或真实用户流量带入练习。

## 这一阶段先把什么讲清楚

- **容器隔离**使用 namespace 分开进程可见的系统资源，用 cgroup 记录和约束 CPU、内存等用量。它不是完整虚拟机，仍共享主机内核，资源限额、网络、文件系统和权限边界需要显式设计。
- **期望状态与调和**把运营者声明的目标与控制器观察到的现状比较，反复采取行动缩小差异。调和能重建 Pod，但不能自动证明应用数据一致或旧写入者已停止。
- **稳定身份与持久卷**让有状态实例在重建后找回稳定名称和存储关联。PV/PVC 表达存储供应与绑定，不等于备份、多副本、应用日志完整或旧节点已被 fencing。
- **SLI、SLO 与 Error Budget**：SLI 是从用户角度测量成功率、延迟或正确性的指标；SLO 是在时间窗口内给这个指标设定的目标；Error Budget 是目标允许的不可靠额度。它用来协调发布速度与稳定性，不是将错误合理化。
- **RPO 与 RTO**：RPO 描述故障后可接受的数据丢失窗口，必须映射到备份、日志、副本或检查点；RTO 描述从故障发生或被确认到恢复可接受服务的时间。“Pod 已 Ready”只可能是 RTO 中的一步。
- **发布、回滚与事故复盘**：发布要限制变更范围、观察关键 SLI 并预定停止条件；回滚要确认代码、配置、Schema 和数据是否真的可逆。事故复盘还原时间线、用户影响、证据、处置与系统条件，目的是改善机制而不是寻找替罪者。

## 组件如何承载这些思想

Kubernetes 用 Pod 承载运行实例，Deployment 调和可替换的无状态副本，StatefulSet 为有状态成员保留序号和卷声明，Service/Ingress 承载访问路径。OpenTelemetry 连接日志、指标和追踪语境，Prometheus 记录时序指标，Grafana 用于查看和联合判断。这些组件可以执行声明的策略，但 SLO 口径、告警责任、数据恢复、fencing 和解除降级的判据仍由系统设计给出。

## 综合项目产物

为已带数据链路的服务提交四项运营证据：一张标明容器、控制器、网络、稳定身份、PV/PVC、状态所有者和故障边界的**部署图**；一张写清 SLI 公式、测量窗口、SLO 目标、Error Budget 与用户影响的 **SLO 表**；一份包含告警含义、证据查询、立即降级、升级与停止条件的**告警 runbook**；以及一份含故障时间线、fencing、恢复起点、数据校验、实际 RPO/RTO 和清理确认的**恢复演练记录**。

## 阶段挑战

在隔离环境中模拟一个有状态节点失联，先不做强制删除，而是说明当前是控制面未见、存储不可达，还是应用协议未恢复。按检测、限制影响、fence 旧写入者、验证卷与日志、恢复、追赶、校验、解除降级的顺序执行，并用时间戳计算实际 RPO/RTO。若超出 SLO 或回滚失败，用事故复盘提出可验证的改进。

## 阅读顺序

先理解容器隔离、期望状态和调和，再区分稳定身份、持久卷与应用恢复；然后用 SLI/SLO、Error Budget、RPO/RTO 连接发布、回滚和事故复盘。接着阅读 [有状态服务恢复：编排、数据与一致性的边界](stateful-recovery.md)，完成四项证据并能用演练记录重算 RPO/RTO 后，进入 ML Systems。
