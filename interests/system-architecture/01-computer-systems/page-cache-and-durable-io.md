# 页缓存（Page Cache）、写入确认与持久化边界

## 一句话理解

一次写入会依次经过应用缓冲区、系统调用、页缓存、写回、设备缓存和稳定介质；“调用成功”只说明其中一个边界被跨过。

## 本页要解决的问题

当事件接入服务在 `write()` 返回后就回复成功，机器随后异常重启时，哪些事件可以被证明已经满足业务确认？

## 本页词汇

| 中文 | English | 在本页中的含义 |
|---|---|---|
| 应用缓冲区 | Application Buffer | 应用进程尚未交给内核的待写数据区域 |
| 页缓存 | Page Cache | 内核暂存文件页、合并读写的缓存层 |
| 脏页 | Dirty Page | 内存内容已更新但尚未完成后续写回的页 |
| 写回 | Writeback | 把脏页推进到文件系统和块设备的过程 |
| 设备缓存 | Device Cache | 设备或控制器接收写入后可能使用的缓存层 |
| 稳定介质 | Stable Storage | 在当前故障模型下可恢复的数据边界 |
| 同步 | Sync | 请求存储栈推进并报告相应写入状态的操作 |
| 业务确认 | Business Acknowledgement | 系统按已声明故障模型向调用方承担的承诺 |

## 在全景业务链中的深入落点

本页负责业务链里的本地 I/O 分支：应用把事件交给 `write()` 后，数据如何经过应用缓冲区、页缓存、回写、设备缓存和稳定介质，以及应用日志在 HTTP 响应前后可能跨过哪些确认边界。它不负责解释线程如何被调度、Kafka 如何完成副本提交、数据库 Buffer Pool 如何执行查询，或日志采集系统如何形成 SLO；这些内容分别由 Network、Replicated Log、Data Systems 和 SRE 页面承接。

## 学习目标

完成本单元后，你能把一次“写入成功”拆成可观察的阶段：应用 buffer 接收、系统调用返回、其他进程可见、Page Cache 变脏、文件系统 writeback、设备缓存接受，以及在给定故障模型下可称为稳定介质的时刻。你还能据此为日志、状态和恢复链路定义业务确认点，而不是把某个 API 返回值当成全部承诺。

## 先修知识

- 熟悉进程地址空间、文件描述符、阻塞 I/O 与基本的崩溃恢复概念。
- 能读懂一段 Node.js 或 Java 文件写入代码；不要求掌握文件系统实现。
- 知道吞吐、尾延迟、RPO（可接受数据丢失窗口）是需要共同权衡的约束。

## 问题场景

推荐平台把用户事件追加到本地文件后，进程立即向上游返回“写入成功”，随后机器异常重启。请区分应用 Buffer、系统调用返回、Page Cache、文件系统写回、设备缓存和稳定介质：哪一步只表示当前进程推进了，哪一步可能已对其他进程可见，哪一步才能成为本业务在明确故障模型下的耐久确认？

## 第一层：底层思想

读完这一层，你应能回答：一次写入依次跨过哪些状态边界，为什么任何单个 API 返回值都不能自动代表业务耐久？

### 先用一条记录走一遍

下面跟踪推荐事件 `E-42`，只讨论常见的 Linux buffered I/O 路径。它是帮助读者建立顺序感的最小例子，不是对所有文件系统、挂载选项或设备的固定承诺；每一步都要以实际观测和故障模型校准。

| 时刻 | 发生的事 | 线程与状态 | 这一步能证明什么 | 还不能证明什么 |
|---|---|---|---|---|
| `t0` | 应用把 `E-42` 放入自己的 buffer | 当前线程仍在用户态，记录只由应用持有 | 应用准备好了待写数据 | 内核、其他进程或设备已经看到它 |
| `t1` | 调用 `write()` 并返回成功 | 线程完成一次系统调用；在常见 buffered I/O 中，指定字节已交给文件 I/O 路径并通常更新页缓存 | 该系统调用按接口接受了指定字节 | 稳定介质已有数据，或业务可以承诺恢复 |
| `t2` | 对应文件页成为脏页 | 内核内存中的文件视图已改变，后续回写仍可能尚未发生 | 内核暂存了新内容 | 设备缓存已刷新，掉电后仍可恢复 |
| `t3` | writeback 把脏页推进到更低层 I/O | 应用线程可能早已继续处理其他请求；写回由内核或同步请求推进 | 数据已离开某个内存缓存边界 | 所有设备缓存、电源保护和故障域都满足耐久要求 |
| `t4` | 应用调用 `fsync()` 并返回成功 | 线程等待文件系统报告同步请求结果；实际含义依赖文件系统、驱动和设备兑现 flush/FUA | 文件系统报告该同步请求成功 | 远端副本、备份、下游消费或任意硬件掉电保证已经成立 |
| `t5` | 应用记录确认并返回 HTTP 响应 | 响应可以与日志写入、Kafka 消费等后台分支并行；日志 `write()` 可能仍在缓冲 | 业务按自己声明的契约承担了某个确认 | 业务链其余组件都已完成或所有状态都已持久化 |

这个例子解释了为什么后文要分别讨论应用 buffer、Page Cache、writeback、`fsync` 和业务确认。若 `E-42` 在 `t1` 后立即得到成功响应，故障调查应先定位 `t1` 到实际确认点之间的窗口；若协议在 `t4` 后才确认，还要写清设备和故障模型的前提。不能因为恢复后看见文件尾部缺失，就反推出具体哪一层一定丢失了数据。

文件 I/O 不是一个单点动作，而是一条状态推进链。**页（page）**是内核按页粒度管理内存和文件内容的基本单位。Linux 的缓冲 I/O（buffered I/O）通常经由**页缓存（Page Cache）**：读可以命中缓存页，写可以先更新缓存页；文件 `mmap` 也由这些文件页提供映射。[Linux iomap 文档](../references/source-matrix.md)将 buffered I/O 描述为默认使用 page cache，脏缓存随后会被回写。

被写过但尚未完成后续回写的缓存页称为 **脏页（dirty page）**。**writeback** 是内核或显式同步请求把脏页提交给更低层文件系统/块层的过程。它使缓存可继续服务更多 I/O，并不自动定义“业务上现在可以承诺不丢”。writeback 完成更不能与最终介质状态混为一层：设备可以先接受写入并向操作系统报告完成，却仍把数据放在**易失设备缓存**中；只有设备把缓存刷新到非易失区域，或在有足够电源保护的缓存中可靠保存，才跨过该设备的稳定介质边界。Linux 的 flush/FUA 机制让文件系统能够要求这一推进，但 `fsync` 的实际耐久仍依赖文件系统、驱动和设备正确兑现相应刷新语义。应用必须把这些条件、电源保护、挂载与部署方式，以及可接受恢复窗口写入自己的确认契约。

因此至少要把下列事件分别记录和讨论：

| 事件 | 可以说明什么 | 不能单独说明什么 |
|---|---|---|
| 应用把记录放入自己的 Buffer | 应用已接受该记录 | 内核、其他进程或设备已见到它 |
| `write()` 返回成功 | 本次系统调用按接口完成 | 已写入稳定介质或业务可恢复 |
| 其他进程从同一文件读到数据 | 其可见性已推进到某个共享状态 | 掉电后仍在 |
| Page Cache 页为脏 | 内存中的文件视图已有新内容 | 后端介质已有新内容 |
| writeback 完成 | 脏页已由文件系统推进到更低层 I/O 路径 | 设备已离开易失缓存或数据已在稳定介质 |
| 设备报告写入接受 | 设备/控制器已接受该 I/O | 数据不在易失设备缓存，或掉电后仍可恢复 |
| `fsync` 返回成功 | 文件系统已报告同步请求成功，并依赖驱动与设备兑现 flush/FUA 等语义 | 任意硬件的掉电保持、远端副本已提交或业务可恢复 |
| 业务确认 | 系统按自己定义的故障模型承担承诺 | 比协议定义更强的恢复或复制语义 |

**顺序 I/O** 倾向连续追加，便于合并写入、预读和批处理；**随机 I/O** 则更受访问位置、缓存命中和设备特性影响。两者都不能只靠“每秒调用数”判断：小的同步写会放大等待，过大的批又扩大故障窗口和尾延迟。

`mmap` 把文件区域映射进进程地址空间，让读写看起来像内存访问；它没有抹掉脏页、回写或恢复边界。所谓“零拷贝”也只能在某条路径上减少某些用户态/内核态复制或上下文切换，不能推导为数据从未移动、CPU 没有工作，或不再需要流控和持久化协议。

`fsync` 是显式请求同步的工具，而不是“耐久”这个业务词本身。Node.js 明确说明 `fs.fsyncSync(fd)` 请求将该文件描述符的数据刷新到存储设备，具体实现取决于操作系统和设备；这正是为什么确认语义必须写出环境与故障模型，而不能从 API 名字猜出固定的掉电保证。批处理将多条记录共用一次同步：它通常提高吞吐，却让一个批次在确认前共享风险窗口。

## 第二层：组件设计落地

读完这一层，你应能回答：在缓冲 I/O、直接 I/O、`mmap` 与同步 API 之间，哪个组件选择符合当前确认契约和工作负载？

**Linux buffered I/O。** 默认路径适合让内核利用 Page Cache 合并读取与写入，应用可配合追加、批量、观测脏页/写回压力和有界同步策略。其代价是 `write()` 的返回与后续 writeback 解耦；如果业务确认依赖落盘，协议必须在恰当位置等待同步，并把失败纳入响应语义。

**Linux direct I/O。** `O_DIRECT` 等路径可绕过 Page Cache；只有当工作负载证据表明应用愿意自己承担缓存、缓冲与一致性协调责任时，才把它作为一个待验证的组件选择。它改变的是数据经过哪一层，而不是确认的含义：直接 I/O 的完成仍不自动成为业务耐久、复制提交或可恢复确认。若依赖 Page Cache 的复用或 `mmap`，尚未量化瓶颈，或无法承担应用侧缓存与 I/O 边界管理，就不应以“更快”为由采用它。

**`mmap`。** 它适合需要以地址空间方式访问文件区域、且能够管理映射生命周期、页故障、并发修改与显式持久化边界的组件；普通文件映射仍经过 Page Cache。映射让写入可在内存访问中发生，却没有定义何时向外确认，且 Java 文档明确 `FileChannel.force()` 对映射缓冲区所作修改未必覆盖。若目标是追加日志的明确确认点或可审计批次，应优先选择能把写入、同步结果和批次 ID 一起记录的常规写入路径，而不要把 `mmap` 当作通用性能或耐久方案。

**Node.js `fs.fsyncSync(fd)`。** 这是一个适合受控实验或专用写入执行路径的同步调用：成功返回只表示底层栈报告了同步请求成功，业务仍须限定文件系统、驱动、设备 flush 和故障模型。Node.js 的同步 API 会阻塞事件循环；因此在同时承载请求处理的事件循环上，若没有隔离或可接受的延迟预算，不应按每条请求直接调用它。选择异步封装或专用写入者也不会增强持久化语义，仍要把同步成功、批次边界和失败响应纳入协议。

**DAX。** DAX 只在底层存储、文件系统、挂载选项和介质支持等条件满足时，才可绕过 Page Cache 的额外副本；实际 `S_DAX` 状态也受这些条件影响。它改变的是一条 I/O 路径，不是针对普通磁盘、网络卷、任意工作负载的通用性能建议，更不会自动建立业务确认、备份或复制语义。应先验证部署栈和故障模型，再评估它是否值得引入。

**Java `FileChannel.force()`。** Java SE 25 将 `force(boolean)` 定义为请求把该通道对文件的更新写入所在存储设备；本地与非本地设备、`metaData` 参数，以及经映射缓冲区写入的数据都有明确的条件差异。它是 Java 层将同步意图交给操作系统的接口，不是“调用后任意宕机都不会丢”的跨层承诺。

**数据库与 Kafka 的自定义确认。** 两者都不能把内核 API 原样暴露成业务协议：数据库必须把日志、数据页、事务提交和恢复规则连在一起；Kafka 还必须把副本、leader、生产者确认和故障条件连在一起。此处不比较谁“更耐久”，而是问：确认对应的是哪份状态、哪个恢复算法、哪些成员或介质、在何种失败下仍可证明。后续 WAL 与 replicated log 单元会继续给出各自的具体契约。

## 第三层：生产实践与真实案例

读完这一层，你应能回答：面对“已确认但重启后文件尾缺失”，应收集什么证据来定位尚未跨过的持久化边界？

案例类型：模拟案例（假设：推荐平台事件接入进程把每条事件追加到单个本地文件；应用在 `write()` 返回后立即记录“写入成功”；未对每条或每批调用 `fsync`；机器在最后一批确认后异常掉电并重启。）

**现象。** 重启恢复时，应用审计表显示最后一批事件已经得到“写入成功”确认，但恢复后的文件尾部停在更早的事件边界；无法仅凭应用响应解释这些确认与文件内容为何不一致。

**证据。** 调查先按时间轴收集，而不预设硬件结论：

- 每条应用确认的时间、事件 ID、批次 ID 与响应状态；
- 记录 `write()` / `fsync` 的系统调用结果和时间（例如受控环境中的 syscall trace），以及是否发生错误或短写处理；
- 配置中实际生效的 `fsync` 策略：逐条、按 N 条、按时间窗、关闭或由其他层承担；
- 重启恢复后文件尾部的字节偏移、最后完整记录 ID、校验结果和尾部截断/解析结果。

**根因。** “写入成功”实际绑定在 `write()` 系统调用返回，而非一个经定义的耐久确认点。按照本案例前提，这些已确认记录不再位于应用 Buffer；风险候选限定在 `write()` 之后的 Page Cache、文件系统 writeback、块层、易失设备缓存与稳定介质之间的尚未覆盖阶段。只有协议在实际调用 `write()` 前就确认时，应用 Buffer 才是已确认记录丢失的候选层。这个模拟不声称特定硬件一定丢失多少数据，也不把文件尾缺失归咎于某个品牌或生产流量。

**处置。** 立即停止把未同步写的成功响应解释为耐久；隔离恢复文件，使用单调事件 ID 与校验识别末尾完整边界；从可验证的上游重放或标记缺口，而不是猜测性补写。同步保留确认时间与实际同步结果，用于确定受影响窗口。

**预防。** ADR 明确确认点和最大允许丢失窗口；以逐条或有界批量同步实现这一窗口；同时监控批大小、批龄、同步耗时、同步失败、确认滞后和恢复尾部差异。演练应使用可丢弃环境和明确注入的进程/主机故障，不能把普通 `kill` 测试宣传成掉电耐久证明。

## 第四层：动手验证与架构判断

读完这一层，你应能回答：如何用可控实验比较同步策略，并把批龄、批大小和失败响应写成可验证的业务确认协议？

### 活动：比较逐条同步与批量同步

- **环境：** 安装 Node.js 的本机；仅使用操作系统临时目录。关闭其他会大量写盘的测试后运行，结果只作本机观察。
- **步骤：** 将下列脚本保存为本地临时文件后执行 `node durable-io-lab.js`。脚本用 `mkdtempSync` 创建一个带随机后缀的专用临时目录，分别写入 200 条记录：第一轮每条 `fs.writeSync` 后调用 `fs.fsyncSync(fd)`，第二轮写完后只调用一次。不要以管理员身份运行。

```js
// durable-io-lab.js
const fs = require('node:fs');
const os = require('node:os');
const path = require('node:path');
const { performance } = require('node:perf_hooks');

const tempDir = fs.mkdtempSync(path.join(os.tmpdir(), 'gulou-page-cache-'));
const count = 200;

function writeCase(name, syncEachRecord) {
  const file = path.join(tempDir, `${name}.log`);
  const fd = fs.openSync(file, 'w');
  const started = performance.now();
  try {
    for (let i = 0; i < count; i += 1) {
      fs.writeSync(fd, `${i},${new Date().toISOString()}\n`);
      if (syncEachRecord) fs.fsyncSync(fd);
    }
    if (!syncEachRecord) fs.fsyncSync(fd);
  } finally {
    fs.closeSync(fd);
  }
  return performance.now() - started;
}

try {
  const eachMs = writeCase('sync-each-record', true);
  const batchMs = writeCase('sync-once', false);
  console.log({ tempDir, count, eachMs, batchMs });
} finally {
  // 删除的目标仅为本脚本刚创建并打印出的专用目录；没有通配符或宽泛路径。
  fs.rmSync(tempDir, { recursive: true, force: true });
}
```

- **预期观察：** 逐条 `fsync` 通常增加总耗时和单记录确认等待；具体比例取决于文件系统、设备、虚拟化、负载与电源保护，不应写成固定倍数。
- **成功条件：** 输出同时包含两次测量与本次专用 `tempDir`，进程以状态 0 退出；学习者能说明第二轮将多少记录置于同一个确认窗口，而非只报告哪个数字较小。
- **清理方式：** 脚本 `finally` 中只删除 `tempDir` 变量指向的、由 `mkdtempSync` 在本次创建的目录。若脚本被中断，先检查输出中的完整目录路径和其命名为 `gulou-page-cache-`，再仅删除那一个目录；不要使用 `rm -rf /tmp/*`、`rm -rf /tmp/gulou-*` 或任何通配删除命令。

该活动不能证明真实掉电耐久：正常退出、进程被终止、虚拟机重启和物理掉电覆盖的缓存与固件行为不同。它只验证一个更窄的假设：同步频率会改变应用等待同步调用的成本，因而必须与确认窗口一起设计。

### 架构判断题

事件接入层要求“确认后最多丢失 250 ms 内的一批事件”，同时允许恢复时从上游重放。请写出：批量同步的最大批龄、最大批大小、同步失败的响应、确认响应中承诺的内容，以及为了验证这项承诺要保存的时间戳和恢复证据。若这些条件无法满足，选择缩短批龄、改为逐条同步或降低确认级别，并说明取舍。

## 常见误区与适用边界

- **误区：** `write()` 成功就是已经持久化。**边界：** 它只说明该调用按接口返回；可见、回写和稳定介质是额外状态，需要协议定义。
- **误区：** Page Cache 是“浪费内存”。**边界：** 它让文件页参与缓存、合并与映射，是 I/O 路径的一部分；问题是是否观测并控制脏页压力、回写和恢复窗口，而非简单禁用。
- **误区：** `mmap` 或“零拷贝”天然更快也更安全。**边界：** 映射生命周期、访问模式、回写和错误处理仍需设计；零拷贝只描述某些复制/切换的减少。
- **误区：** DAX 是所有高性能存储的默认答案。**不使用场景：** 部署栈未确认文件系统、挂载、介质和 `S_DAX` 条件，或问题主要是复制协议、恢复逻辑、随机访问模式时，不应为了“绕过 Page Cache”引入 DAX；保留 buffered I/O 并先改善批处理与观测。
- **误区：** `O_DIRECT` 必然绕开所有性能问题。**不使用场景：** 当应用无法可靠处理对齐、自己的缓存和 I/O 深度，或工作负载受同步确认/网络复制而非 Page Cache 限制时，不应贸然使用；先量化瓶颈并选择能够承担缓存与恢复责任的方案。

## 掌握度检查

1. **解释：** 为什么 `write()` 成功不等于业务耐久？用“应用 buffer、Page Cache、writeback、设备/稳定介质、业务确认”逐层说明，并标出每层缺少的证据。
2. **应用：** 对“允许最多丢失 250 ms、必须记录确认时间、可以上游重放”的接入层，何时批量 `fsync` 合理？给出批龄/批量上限、确认点和同步失败处理，而非只说“性能更好”。
3. **迁移：** 将本单元的确认边界迁移到数据库 WAL 或 Kafka 副本确认：各自还必须增加哪一种恢复或副本证据，才能让业务确认有意义？
4. **不使用：** AI 若建议所有写都使用 `mmap` 或 `O_DIRECT`，你应追问什么？至少覆盖访问模式、缓存归属、对齐/生命周期、故障模型、同步语义、恢复流程与可观察证据；给出一个继续使用 buffered I/O 的替代方案。

### ADR：推荐事件接入层的本地确认与恢复窗口

**状态：** 建议采用，待以目标部署环境压测和恢复演练验证。

**上下文：** 接入层需要在本地文件追加事件，并向调用方解释“成功”的含义。仅把 `write()` 返回当确认会把 Page Cache 及后续路径的风险隐藏在业务协议中。

**决策：** 确认点定义为：事件已写入追加日志，且包含该事件的有界批次已完成一次成功的文件同步调用；响应记录事件 ID、批次 ID 与确认时间。同步在以下任一条件先到时触发：最大批龄（不超过 250 ms）、最大记录数阈值或最大字节数阈值。批龄以首条未确认记录进入批次至同步开始的时间度量；记录数与字节数分别计量，不能与毫秒比较或混为一个 `min`。两个容量阈值不在本文虚构固定值，须通过目标环境的压测和恢复演练确定、记录并随部署发布。实际承诺仍须在文件系统、驱动、设备 flush/电源保护语义验证后发布。同步失败时不返回该批耐久成功，保留错误和批次证据，并按上游幂等键重试或重放。

**后果：** 批量同步减少每条记录等待同步的次数，却让同一批的尾部事件共享最长一个批龄的未确认窗口；逐条同步可缩小该窗口，但可能明显增加确认延迟。该 ADR 不把本地同步等同于跨机副本、备份或任意硬件掉电保证；后续 WAL、Kafka log 和 checkpoint 设计必须分别补齐恢复和副本语义。

**验证与回滚：** 记录批龄、批大小、同步延迟/失败、确认滞后及恢复尾部差异；在可丢弃环境注入明确故障并用上游重放校验。若无法满足约定窗口或同步错误率/尾延迟不可接受，降低批龄或改为逐条同步；若本地文件不再是适当持久层，停止在此层提供耐久确认，改由具备所需复制与恢复契约的下游系统确认。
