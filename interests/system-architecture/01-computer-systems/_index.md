# Computer Systems

## 阶段目标

建立一条从应用代码到操作系统再到存储设备的因果链，用它解释单机服务为什么阻塞、排队或丢失吞吐量。重点不是背术语，而是同时说清操作系统正在做什么，以及架构师能从指标、追踪和实验中观察到什么。

## 进入条件

已经完成阶段 0 的请求/约束表和容量估算，并能选出一条需要观察的请求路径。最好准备一个可运行的单机服务，以便记录线程、内存、队列和 IO 指标。

## 先看一条业务链：一次推荐请求如何穿过系统

先用一条推荐平台的示意链建立全局直觉，再分别进入操作系统、网络、分布式和数据系统页面。它不是每个请求都必须经过的固定顺序：数据库读取可能是同步关键路径，Kafka 消费和特征更新通常是异步分支；只有在架构明确等待它们时，异步分支才会成为 HTTP 响应的前置条件。

```text
HTTP 请求
  → 网络栈 / accept queue
  → 进程与线程被调度
  → handler / event loop
      ├─ 同步读路径：数据库连接
      │    → Buffer Pool 命中
      │    → 或未命中后读取 OS Page Cache / direct I/O / 存储设备
      └─ 异步事件路径：Kafka client buffer
           → broker append
           → follower replication / commit / high watermark
           → consumer 读取并更新特征或状态
  → 响应序列化
  → 应用日志 write（可能仍在缓冲区）
  → HTTP 响应
```

阅读这条链时，每一步都先问四个问题：状态由谁拥有，线程在计算还是等待，哪一个队列或缓冲正在积累，以及“成功”跨过了哪个确认边界。Kafka 的 high watermark 是复制日志的协议可见性边界，不等同于物理磁盘已经稳定持久化；事件时间水位线则属于流处理语义，不能与它混用。数据库的 Buffer Pool 未命中也不必然是进程 Page Fault：数据库可能走操作系统页缓存，也可能使用 direct I/O；只有具体实现和观测证据才能确定路径。

这一节只负责预览，不替代后续深入页面：[Network](../02-network/_index.md)解释 HTTP 连接、超时、重试和排队；[Replicated Log](../03-distributed-systems/replicated-log.md)解释 Kafka 写入、复制、提交、高水位与消费可见性；[Data Systems](../04-data-systems/_index.md)解释数据库读路径、存储布局和查询执行；[Page Cache、写入确认与持久化边界](page-cache-and-durable-io.md)解释本地日志写入和落盘确认；[综合评审](../capstone/log-state-recovery-review.md)再把它们放回同一条故障时间线。

## 这一阶段先把什么讲清楚

把一次写请求按因果顺序拆开：

1. **进程与线程**：操作系统给进程隔离的地址空间和资源，为可运行线程分配 CPU；架构师可以观察线程状态、上下文切换、CPU 使用率和调度等待。这里的“CPU 等待”优先指线程在 runnable queue 中等待运行的时间，不把 I/O 阻塞或 Linux 的 `iowait` 统计简单当成同一个指标。
2. **虚拟内存与缺页异常（Page Fault）**：操作系统维护虚拟地址到物理页的映射，访问尚未驻留的页时可能暂停线程并装入页面；应区分 minor/major page fault 与 swap。架构师可以观察常驻内存、缺页次数、换页和停顿，区分应用分配压力、文件页未命中和实际物理内存压力。
3. **文件描述符、句柄与 socket**：文件描述符是进程内的整数索引，可以指向普通文件、管道或 socket；普通文件通常有关联的文件偏移，socket 则主要关联连接状态和收发缓冲。“句柄”是更泛化的资源引用说法，不能把它们都解释成有文件当前位置。架构师可以观察打开数量、上限、泄漏以及系统调用错误，判断连接或文件资源是否耗尽。
4. **页缓存与回写（Page Cache / Writeback）**：操作系统可能先把写入放入内存页并标记为脏页，随后异步回写设备；架构师可以观察脏页、回写量、同步调用耗时和磁盘延迟，分清“应用已返回”“操作系统可见”“设备已持久化”与“崩溃后可恢复”。
5. **缓冲**：操作系统和应用用内存聚合小读写、减少系统调用，但也让尚未下沉的数据和等待时间增加；架构师可以观察缓冲区占用、批次大小、刷新频率和端到端延迟，判断吞吐收益是否换来了过长等待。
6. **背压**：当下游消费速度低于上游生产速度时，操作系统的套接字或 IO 队列会填满并让写入阻塞或失败，应用队列也会继续放大等待；架构师可以观察队列深度、阻塞时间、拒绝数和高分位延迟，决定限流、降级或减少并发。

这条链还会受到 CPU 缓存、锁、垃圾回收和批处理影响，但任何解释都应回到“哪个资源在做什么、哪项证据能验证”。

## 组件如何承载这些思想

先用 **Linux 操作系统**观察调度、内存、文件描述符、页缓存和设备 IO，再用 **Java 虚拟机（JVM）**理解堆、垃圾回收（GC）、即时编译（JIT）和线程运行时怎样叠加在操作系统之上。Netty 可作为事件循环和缓冲的例子，Kafka 与数据库存储引擎可作为页缓存、批处理和持久化边界的例子；这些名称用于验证模型，不是本阶段的组件清单。

## 综合项目产物

为单机服务产出一张从应用发起写入，到系统调用、页缓存、回写设备，再到收到**持久化或可恢复确认**的时间线。时间线应标注线程何时运行或等待、数据位于哪一层、确认语义是什么，并附上线程、内存、队列与 IO 的观测证据。

## 阶段挑战

制造一个下游变慢的场景，说明缓冲何时转为排队、排队何时转为背压，以及它们如何改变吞吐和尾延迟。仅凭 CPU 利用率不足以定位瓶颈；请组合线程状态、缺页、文件描述符、队列深度、回写和设备延迟，给出可证伪的判断。

## 阅读顺序

先按进程/线程、虚拟内存/缺页异常、文件描述符、页缓存/回写、缓冲、背压的顺序建立因果链；再阅读 [Page Cache、写入确认与持久化边界](page-cache-and-durable-io.md)，校准“写入成功”的不同含义。完成应用写入到持久化或可恢复确认的时间线与阶段挑战后，进入 Network。
