# Data Systems

## 阶段目标

从数据如何被写入、读取、更新、扫描和恢复出发选择存储结构。完成本阶段后，你应能说明一种存储选择服务于什么访问模式，并用读写放大、延迟、吞吐、耐久性与恢复证据描述代价。

## 进入条件

已经定义事件、关键状态和主要访问模式，并能区分分布式系统中的复制提交与单节点持久化。准备一组具体查询及其数据量、读写比例、延迟目标和恢复要求，而不是先选数据库品牌。

## 在全景业务链中的深入落点

本阶段负责同步读路径和数据库存储路径：请求进入连接池与数据库执行线程后，先查 Buffer Pool，再根据查询计划访问索引、数据页或分析列；未命中时可能读取操作系统页缓存，也可能使用 direct I/O，不能把“数据库页未命中”直接写成进程 Page Fault。数据库写入与提交的 WAL 边界由[Write-Ahead Log：从提交确认到崩溃恢复](write-ahead-log.md)深入解释；本阶段后续还要补齐查询执行和批流正确性的正式单元。

## 这一阶段先把什么讲清楚

- **行式存储与列式存储**回答“一次访问需要整行还是少数列”：行式布局适合按记录读取和更新，列式布局适合只扫描少量列的聚合分析，并便于压缩与向量化执行。
- **B+ 树与 LSM 树**回答“点查、范围读和持续写入怎样权衡”：B+ 树维护有序页，便于点查与范围扫描；LSM 树先把写入变成顺序追加，再通过分层合并换取写吞吐，同时承担读放大、写放大和压实成本。
- **预写日志（WAL）**回答“数据页尚未落盘时如何确认提交和崩溃恢复”：先持久化描述变更的日志，再异步更新数据页；因此日志落盘、数据页落盘和事务提交必须分开描述。
- **多版本并发控制（MVCC）**回答“读写如何并发且各自看到一致视图”：存储保留版本并按事务可见性规则选择记录，同时需要回收旧版本并处理长事务带来的空间压力。
- **缓冲池（Buffer Pool）**回答“哪些磁盘页应驻留内存”：数据库管理页缓存、淘汰和脏页刷新；命中率、脏页比例、淘汰和 IO 等待是判断内存是否真正改善访问模式的证据。
- **查询执行**回答“声明式查询如何变成资源工作”：查询规划器依据统计信息选择访问路径和连接顺序，执行引擎完成扫描、过滤、排序、聚合与连接；执行计划、实际行数、CPU、内存、溢写和 IO 揭示估算与现实的差距。

分区、副本、倒排索引和全文检索继续回答更具体的扩展与检索模式，但不能替代上述访问模式分析。

## 组件如何承载这些思想

MySQL 与 PostgreSQL 可用于观察行式存储、B+ 树、WAL、MVCC、缓冲池和查询计划；RocksDB、HBase 与 Cassandra 展示 LSM 系结构的不同取舍；Lucene 与 Elasticsearch 承载倒排检索；ClickHouse 与 Doris 展示列式分析。Redis 可用于有明确失效与一致性边界的缓存。它们用于比较访问模式与证据，不要求逐一部署或精通。

## 综合项目产物

为事务、缓存、搜索、分析和特征场景提交一份存储决策记录。每项选择至少包含：数据与访问模式、候选结构、预期读写路径、提交与恢复语义、容量和成本假设，以及基准测试或执行计划等验证结果。证据应能说明为何选择行/列布局、B+ 树/LSM 树、索引和缓存策略，也应记录被拒绝方案及其边界。

## 阶段挑战

给定同一份数据的点查、范围更新、全文检索和大规模聚合需求，为每种访问模式选择存储路径；再用执行计划、命中率、写入与压实指标、WAL 刷盘延迟和恢复演练，评审索引、分区、副本选择在读写负载、数据丢失窗口与成本上的边界。

## 阅读顺序

先比较行式与列式布局，再比较 B+ 树与 LSM 树；接着阅读 [Write-Ahead Log：从提交确认到崩溃恢复](write-ahead-log.md)，然后学习 MVCC、缓冲池和查询执行如何共同影响可见性与性能。完成有证据的存储决策后，沿主路线进入 Data Architecture。
