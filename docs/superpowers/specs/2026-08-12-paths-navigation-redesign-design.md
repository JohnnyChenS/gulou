# 学习路径与网站导航重构设计

日期：2026-08-12

状态：待用户审阅

## 背景

`gulou-core` 已经有 `paths/` 目录，但当前页面同时承担了几种不同工作：介绍路线、列出文章、说明前置关系、安排执行任务，以及记录未来待创建内容。网站生成器又按目录和同级文件生成导航，因此用户看到的是知识分类，而不是“我现在先看什么、看完做什么”。

现有 `paths/learning/_index.md` 已经包含按年龄入口、选择下一步和学习主题说明，是可以继续利用的基础；问题在于这些内容集中在一篇较长的说明中，没有形成短路线，也没有被首页和文章页突出显示。

## 目标

1. 把 `paths/` 定义为网站唯一的路线层，不新增平行的“使用指南”目录。
2. 让首页同时支持两种入口：按孩子年龄开始、按当前问题开始；默认优先呈现年龄入口。
3. 让每条主路线明确给出第一步、有限的主步骤、一个可执行动作和下一步。
4. 让用户从任意文章回到路线，并在路线中前进或退回。
5. 保留现有知识文章和深入领域路径，避免复制正文或为了导航大规模搬迁内容。
6. 让手机端也能看到当前路线和下一步，不依赖隐藏的桌面侧栏。

## 非目标

- 本次不把网站改造成需要登录、记录完成状态或保存个人进度的应用。
- 本次不为所有文章建立自动推荐图谱，也不要求一次性补齐所有兴趣领域。
- 本次不重写现有知识文章的医学、安全或发展内容；发现内容问题时单独记录处理。
- 本次不优先实现每日/每周执行日历。先解决阅读顺序和下一步，再扩展执行路线。

## 信息架构

`paths/` 采用三层职责：入口路线、主题路线、知识路径。

```text
paths/
├── _index.md                         总入口
├── learning/
│   ├── _index.md                     学习与探索总路线
│   ├── ages/
│   │   ├── _index.md                 按年龄开始
│   │   ├── 0-3.md
│   │   ├── 3-6.md
│   │   ├── 6-9.md
│   │   ├── 9-12.md
│   │   ├── 12-14.md
│   │   └── 14-18.md
│   ├── questions/
│   │   ├── _index.md                 按问题开始
│   │   ├── learning-habits.md
│   │   ├── school-learning.md
│   │   └── interest-discovery.md      由现有兴趣路线迁入
│   └── ...
├── 0-3/
│   ├── cognitive-psychological.md     领域知识路径
│   └── physical.md
└── ...
```

职责约定：

- `paths/_index.md` 只做总入口，提供年龄、问题和主题路径的选择，不再堆放路径规范、文章计数和待创建清单。
- `paths/learning/_index.md` 是学习与探索的总路线，解释这条路线适合谁，并把用户送到年龄路线或问题路线。
- `paths/learning/ages/` 回答“这个年龄先看什么”。每个年龄页只挑 2–4 个主步骤。
- `paths/learning/questions/` 回答“我现在遇到什么问题，先做什么”。现有 `paths/learning/interest-discovery.md` 迁入该目录，其他问题页沿用同一格式；它们链接到年龄路线和现有知识页，不复制正文。
- `paths/0-3/` 等现有领域路径保留为深入路线，不再承担网站第一入口。
- `stages/` 下的文章仍是知识源，路线页只负责选择、顺序和行动。

## 路线页面模板

年龄路线和问题路线使用同一套可读结构：

```text
路线标题
一句话说明：适合谁，从什么情况开始

一、先判断
- 当前是否适合从这条路线开始
- 风险或持续影响功能的情况应转向专业支持

二、阅读顺序
步骤 1：先理解什么
- 阅读：一篇或少量相关文章
- 动作：本步骤只做一件事
- 观察：用具体行为判断是否需要调整

步骤 2：接着练什么
...

三、本周只做一件事

四、什么时候进入下一步

五、补充阅读
```

内容规则：

- 年龄路线保留 2–4 个主步骤；问题路线保留 3–5 个主步骤。
- 主步骤必须同时有阅读链接、一个动作和一个观察点。
- 其他文章放入“补充阅读”，不参与默认顺序。
- “完成”表示用户完成一次理解、尝试或观察，不表示孩子达到固定发展标准。
- 涉及持续影响学习、情绪、身体或家庭功能的情况，要明确提示联系老师、儿科、发育行为或心理健康专业人员。
- 导航文案采用直接、克制的中文，例如“先看这里”“今天做一件事”“下一步”，避免宣传式和口号式表达。

## 路线元数据

路线页增加少量网站需要的 frontmatter，正文仍是主要内容来源：

```yaml
page_type: route
route_group: learning-age
route_key: 0-3
route_order: 1
route_label: 0–3 岁
route_next: ../3-6.md
```

问题路线使用 `route_group: learning-question`，并保留问题名称作为 `route_label`。元数据只描述路线身份和相邻关系，不把所有推荐逻辑塞进 YAML；具体步骤、动作和判断仍写在 Markdown 中，便于人阅读和审阅。

现有领域路径可以暂时保留原 frontmatter。网站需要时可增加 `page_type: knowledge-path`，以便和入口路线使用不同的导航样式。

## 网站导航设计

### 首页

首页首屏改成决策入口，而不是先展示项目愿景：

```text
从这里开始

孩子现在多大？
[0–3 岁] [3–6 岁] [6–9 岁] [9–12 岁] [12–14 岁] [14–18 岁]

我现在想解决什么？
[学习习惯] [学校学习] [发现兴趣] [亲子互动] [父母状态]

想直接查资料？
[浏览全部知识]
```

年龄入口默认排在问题入口之前；两者都链接到 `paths/` 下的路线页。

### 顶栏

顶栏使用任务导向的顺序：

```text
开始使用   按年龄   按问题   主题路径   知识参考
```

“知识参考”保留对完整知识库和参考资料的访问，但不再与“开始使用”混在同一层级。

### 路线页和文章页

- 路线页显示当前路线名称、步骤总数、当前步骤和下一步。
- 文章页顶部或正文前显示“返回当前路线”；正文后显示“上一步 / 下一步”。
- 直接从搜索或外部链接进入文章时，如果文章被某条主路线引用，显示对应路线入口；没有路线归属的文章仍可正常阅读。
- 桌面端侧栏按路线步骤分组，而非只列当前目录的同级文件。
- 移动端将路线步骤渲染为正文顶部的简短导航卡片或折叠区域，不能因隐藏侧栏而失去路线信息。
- 显示标题时优先使用 frontmatter 的 `name`，没有时才回退到清理后的文件名。

## 构建器调整边界

网站构建器需要新增路线识别和渲染能力，但不引入客户端状态管理：

1. 读取 `page_type`、`route_group`、`route_order`、`route_next` 等字段。
2. 为路线页生成路线步骤导航和下一步卡片。
3. 为被路线引用的知识页生成返回路线和相邻步骤链接。
4. 首页使用明确的路线入口数据，避免手写大量重复卡片。
5. 对缺少元数据、目标链接不存在或路线顺序断裂的情况输出构建警告；不因单个补充文章缺少路线信息而阻断网站生成。

不在本次范围内的构建能力：用户登录、阅读进度持久化、个性化推荐、全文搜索服务和自动推断文章前置关系。

## 分阶段实施

### 第一阶段：学习与探索样板

- 重写 `paths/_index.md` 和 `paths/learning/_index.md`。
- 新增年龄路线和问题路线的索引及首批页面。
- 修正学习路径中的文章计数、链接和命名。
- 调整首页、顶栏、路线侧栏和移动端路线提示。
- 构建网站并检查链接、路线顺序和手机布局。

### 第二阶段：迁移其他路径

- 按同一模板整理育儿指导、语言学习、脑健康和其他兴趣路径。
- 只在某条路线有明确使用场景时增加问题入口，避免为了完整而制造导航页面。
- 继续保留知识库的完整浏览入口。

## 验收标准

### 用户体验

- 新用户从首页两次点击内可以进入一个年龄路线或问题路线的第一步。
- 每条主路线都能回答“先看什么、做什么、观察什么、下一步是什么”。
- 从任意主路线文章可以返回路线，并能进入下一步。
- 手机端可见当前路线和下一步。
- 导航中不再直接显示 `interest-discovery` 等原始文件名。

### 内容完整性

- 现有知识文章仍可访问，原有深度路径不因入口重构而丢失。
- 主步骤链接全部有效；补充阅读链接不被错误标记为主步骤。
- 年龄路线不把年龄当成硬性诊断或截止日期。
- 安全、医疗、心理相关页面继续保留明确的专业支持和风险提示。

### 构建质量

- `cd website && npm run build` 成功完成。
- 构建输出不出现缺失路线目标、断裂相邻关系或无标题页面的警告。
- 对新增路线页面执行 Markdown 链接检查和 frontmatter 检查。
- 不以 `npm test` 作为成功依据，除非项目后续真正配置测试脚本。

## 风险与取舍

- 增加路线页会带来少量内容维护成本，但比在每篇知识文章上补齐复杂推荐元数据更容易审阅和修改。
- 同一篇文章可能被多个问题路线引用，因此“下一步”关系应归属于路线，而不是写死在知识文章正文中。
- 如果路线步骤过多，网站会重新变成目录。默认限制主步骤数量，完整内容继续放在补充阅读和知识路径中。
- 生成器改动应先支持显式元数据，不自动猜测顺序；人工维护的路线更容易发现错误，也更符合安全敏感内容的审阅要求。
